How this is built

A Spring Boot service that fetches current headlines, has a locally hosted model summarize them, and serves the result to both people and programs.

Modules

One deployable artifact, four modules with enforced boundaries. Each exposes a small public API and hides the rest in an internal package that siblings cannot import — a rule checked by the build, not by code review.

  • news — retrieving and normalizing headlines. The NewsAPI wire format and the credential never leave this module.
  • summarization — turning documents into a structured summary. It takes its own input type rather than the news module's, so the two stay independent siblings instead of a chain.
  • brief — composes the two and publishes them, as JSON and markdown for programs and as these pages for people.
  • shared — cache setup, error vocabulary, resilience wiring.

The model returns data, not prose

Spring AI derives a JSON schema from a record and parses the reply back into it. That is why this page and the JSON response cannot disagree: both render from the same typed value. An earlier version asked the model for an HTML page and recovered it by slicing characters off a markdown fence, which broke the moment the model phrased its answer differently.

Failure is the normal case

Two network dependencies sit behind every request. Timeouts are explicit, transient failures are retried with backoff and jitter, and a rejected API key is not retried at all — repeating it only burns quota. Repeated failures open a circuit breaker so calls fail fast instead of piling up.

Caching deliberately sits ahead of that breaker. When an upstream is down, results the application already holds are exactly what should still be served.

This page you are reading

Server-rendered Thymeleaf, progressively enhanced with htmx. Every route works with JavaScript disabled; htmx only adds the partial swap that makes a slow generation show progress instead of freezing the tab.
